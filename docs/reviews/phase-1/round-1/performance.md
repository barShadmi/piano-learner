# Performance and audio latency · phase 1 · round 1
Score: 8/10

There are no Blocking items. The live-sound path is built right, so every item below is Polish.

**What I checked and ran**
- **Audio thread.** I read `EngineCore::process`, `Mixer`, the piano voice and the WASAPI and cpal callbacks. The audio thread gets its notes through single-producer rtrb rings that never lock. Commands are `Copy`, and `next_bank` / `give_back` mean the audio thread never frees a piano bank. The clock read is an atomic load plus QueryPerformanceCounter. The WASAPI render loop runs in the "Pro Audio" MMCSS class and never allocates or logs.
- **MIDI path.** The MIDI callback only uses `try_lock` to push into the ring, then wakes the forwarder thread. The UI hears about keys on a separate path: forwarder thread, then a non-blocking threadsafe function, then `webContents.send`. So nothing in the UI can delay sound.
- **No Web Audio.** There is no `AudioContext` or `requestMIDIAccess` anywhere in `src`.
- **Tests.** `cargo test --release` passes: 240 + 6 tests. That includes the 6 no-allocation and no-free tests in `native/audio-engine/tests/no_alloc.rs`, which cover the bank swap, the song ring and a full latency ring. The piano load took 1.31 s for 120 samples.
- **Render time (my own scratch benchmark, outside the repo).** 64 sustained piano voices, 128 frames at 48 kHz: 125 µs on average, 966 µs at worst, against a 2,667 µs budget. This is a cloud VM, so the worst case includes scheduler noise.
- **Memory.** The decoded piano bank takes about 196 MB in the Electron main process (120 samples, each cut to at most 10 s, 48 kHz stereo 16-bit). There is one shared copy.
- **Frame rate.** I ran the falling-notes e2e under xvfb: `data-fps=60`, passed. This only covers the short Canon sample.
- **Delay estimate.** At 128 frames in exclusive mode: wait up to 2.7 ms, plus about 2 periods of output (about 5.3 ms), plus 1 ms for USB. That is about 7 to 9 ms. If the device's shortest period is 3 ms, p95 lands near 10 ms. Only Bar's run on his PC will settle this.

## Must fix to reach 10
1. Polish · `native/audio-engine/src/output/wasapi_exclusive.rs:393-400` · In exclusive mode, an underrun is counted only when the device event takes longer than 50 ms (`EVENT_WAIT_MS`). A late buffer (a crackle) is never counted. So "Sound gaps (underruns)" in the delay report will nearly always say 0, even when the sound crackles. · Good: keep the last wake time in the loop and count an underrun when the gap since the previous event is more than 1.5 × `buffer_frames / sample_rate`. Or compare the `IAudioClock` position against what was written. Add a unit test for that gap check as a pure function.
2. Polish · `native/audio-engine/src/core/mixer.rs:202-217` with `src/piano/voice.rs:96-107` · When all 64 voices are busy (pedal held through a passage), `steal` makes the new note wait for a 2 ms fade before it starts. That adds 2 ms of lag the delay test cannot see, because it stamps the moment the callback picks the note up, not the moment the sound starts. · Good: the new note starts at once on the chosen voice while the stolen sound fades out separately (for example a small fixed array of fade-out voices in `Mixer`). Or, at the least, count steals in `EngineStats` and show them in the report. Add a test that a note on a full mixer is heard within the same callback.
3. Polish · `src/shared/latency.ts:126` and `native/audio-engine/src/output/mod.rs:107-111` · The report says "The sound card figure was measured when sound started." For WASAPI it is not measured: it is the buffer plus the driver's reported `GetStreamLatency` (`wasapi_exclusive.rs:131-132`). Only cpal measures it (`playback - callback`). `latency_ms` also has two doc comments that contradict each other. · Good: the wording depends on the backend, for example "reported by the sound driver" for WASAPI and "measured" for cpal and ASIO. Keep one accurate doc comment.
4. Polish · `native/audio-engine/src/piano/bank.rs:169` (`load_dir`) and the session start in `output/mod.rs` · The 196 MB of samples is ordinary pageable memory. Windows can trim the working set (when the window is minimised, or when memory is tight). The next key press after a long pause can then page-fault on the audio thread, which means a late or crackling note. · Good: after loading, raise the minimum working set (`SetProcessWorkingSetSizeEx`) and `VirtualLock` the sample data on Windows, falling back quietly if refused. Note in the Sound status whether the lock worked.
5. Polish · `native/audio-engine/tests/` (missing) · No test guards the render-time budget, so a later change to the voice code could slow it down without anyone noticing. · Good: add a release-only test (`#[cfg(not(debug_assertions))]`) that loads the real bank and renders 64 sustained voices for 3,000 × 128-frame calls. It should assert a mean under 25% of the 2.67 ms budget (today it is about 5%).
6. Polish · `e2e/app.spec.ts:220` and `src/renderer/src/falling/FallingNotes.tsx:341-351` · The frame-rate test only asserts at least 30 fps, on a short song, and records only the average. One slow frame (a stutter) would not show. · Good: FallingNotes also writes a `data-long-frames` count (frame gaps over 20 ms) and the worst gap in the last second. The e2e plays a dense generated song (about 2,000 notes, 10-note chords) and asserts fps ≥ 55 and a long-frame rate under 1%, logging both. Keep the CI floor loose if the VM needs it.
7. Polish · `src/main/songStore.ts:25-41` (called from `src/main/ipc.ts:27`) · `listSongs` reads and parses every full song JSON with synchronous calls on the Electron main thread each time the library opens. That thread also passes key events to the screen, so a big library delays the keyboard lights. It does not affect sound. · Good: keep a small `index.json` of summaries, written by `saveSong`, or read the files with `fs.promises` in parallel. A test that 100 songs list in under 50 ms.
8. Polish · `src/renderer/src/screens/Latency.module.css:79` · The delay-test progress fill animates `width`, which is a layout property. · Good: the fill stays at full width with `transform-origin: left`, `transform: scaleX(shown / KEYS_NEEDED)` is set inline in `Latency.tsx:160`, and the CSS uses `transition: transform var(--dur) var(--ease)`.
9. Polish · `native/audio-engine/src/song/mod.rs:26` (`SPIN_US = 3_000`) · The song thread busy-waits for 3 ms before every event, even when the high-resolution waitable timer exists (Windows 10 1803 and later). On dense music that burns CPU and battery for nothing. · Good: a short spin (about 500 µs) when `win::Sleeper` has a high-resolution timer, and 3 ms only on the `timeBeginPeriod` fallback. The song timing tests stay green.
