# Performance and audio latency · phase 1 · round 2
Score: 9/10

There are no Blocking items. The round 1 fixes left the live-sound path alone. Every item below is Polish: five were moved to `docs/reviews/phase-1/later.md` and are listed again so the list stays complete, and two are new and small.

**What I checked and ran this round**
- **Live sound path.** No commit after e844821 touches `core/`, `piano/` or the audio callbacks. The changes in `output/mod.rs` and `output/cpal_out.rs` are error words and one doc comment, all on the open/error path, not the callback. Removing `latency_samples` only removes a napi export. The audio thread still never allocates, locks or waits. `cargo test --release` passes: 242 + 6, including the 6 no-allocation tests in `tests/no_alloc.rs`.
- **Song player timing.** In `native/audio-engine/src/song/mod.rs:344-350` the thread calls `clock.thread_begin()` (which makes the high-resolution timer) before `run_song`. `run_song` reads `clock.spin_us()` once at line 241, before its loop. So the 500 µs spin really applies when the timer exists, and the fallback stays 3 ms. `has_high_res_timer` (`song/win.rs:64-66`) takes the Sleeper mutex once per song, on the song thread, never on the audio thread. The new virtual-time test `a_precise_clock_sleeps_until_half_a_millisecond_before_an_event` passes, and so do the old 3 ms tests. Real timing is still only checked at Bar's gate, as later.md says.
- **Falling-notes frame loop.** `restyle` runs only when a slot's note, width, height or theme changes (`FallingNotes.tsx:366`). The height is the note's full length, not a clipped one, so a note restyles once when it comes into view, not every frame. The things that cost something all happen only in restyle: `chooseLabel`, `label.style.fontSize = …`, `label.text = …` and the stripe `rect`. Labels come from the pre-made `FULL` table, and widths come from the `glyphWidth` table, measured once. The per-frame code only sets x, y and visible, then renders. Under xvfb the falling-notes e2e gives `data-fps=60` and 3 tests pass. Vitest for `falling/` and `songStore` passes (93 tests).
- **Play screen.** The new `activity` state and the lead-in `setTimeout` change only on button presses and timer events. No React state is set per frame.
- **Measured delay.** There is no sound device in the cloud, so the round 1 estimate stands: about 7 to 9 ms at 128 frames in exclusive mode. Bar measures it at his gate.

## Must fix to reach 10
1. Polish (in later.md) · `native/audio-engine/src/output/wasapi_exclusive.rs:393-400` · In exclusive mode an underrun is counted only after a 50 ms event timeout. A late buffer (a crackle) is never counted, so "Sound gaps" in the delay report will almost always say 0. · Good: keep the last wake time and count a gap when the time between events is more than 1.5 × `buffer_frames / sample_rate`. Put the check in a pure function with a unit test.
2. Polish (in later.md) · `native/audio-engine/src/core/mixer.rs:202-217` and `src/piano/voice.rs:96-107` · When all 64 voices are busy, the new note waits for a 2 ms steal fade, and the delay report cannot see that wait. · Good: start the new note at once and fade the stolen voice in a small fixed array of fade-out voices. At the least, count steals in `EngineStats` and show them in the report. Add a test that a note on a full mixer is heard in the same callback.
3. Polish (in later.md) · `native/audio-engine/src/piano/bank.rs:169` (`load_dir`) · About 196 MB of samples sit in pageable memory. If Windows trims the working set (window minimised, or memory tight), the next key can page-fault on the audio thread. · Good: on Windows, raise the minimum working set with `SetProcessWorkingSetSizeEx` and `VirtualLock` the sample data. If that is refused, carry on quietly and show in Sound status whether the lock worked.
4. Polish (in later.md) · `native/audio-engine/tests/` (missing) · No test guards the render-time budget. · Good: a release-only (`#[cfg(not(debug_assertions))]`) test that renders 64 sustained voices for 3,000 calls of 128 frames, and asserts a mean under 25% of the 2.67 ms budget.
5. Polish (in later.md) · `e2e/app.spec.ts:222-224` and `src/renderer/src/falling/FallingNotes.tsx:398-408` · The frame test only asserts at least 30 fps on the short Canon sample, and records only the average, so one stutter would not show. · Good: add a `data-long-frames` count (frame gaps over 20 ms) and the worst gap. Play a dense generated song (about 2,000 notes, 10-note chords). Assert fps ≥ 55 and a long-frame rate under 1%, and log both.
6. Polish (new) · `src/main/songStore.ts:64-67` (`getSong`, used by `songs:get` in `src/main/ipc.ts:24-27`) · `listSongs` is now async, but opening a song still reads and parses the whole file with `readFileSync` on the Electron main thread. That thread also passes key events to the screen, so a large imported song (up to 20 MB) can delay the keyboard lights for that moment. Sound is not affected. · Good: make `getSong` async with `fs.promises.readFile` (the async `readSongFile` already exists), and make the `songs:get` handler async. Keep the UUID check before any file is opened. Also add the 100-songs-listed-in-under-50-ms test from later.md.
7. Polish (new, minor) · `src/renderer/src/falling/label.ts:730-731` · `chooseLabel` makes two small arrays (`sizeList`, `texts`) on every call. It runs only in restyle, so it does not hurt 60 fps today. But it goes against the file's own note that "choosing a label never makes a new string" and the frame loop's no-allocation rule. · Good: replace the arrays with fixed checks in the same order (full at md, full at sm, letter at md, letter at sm). Then `chooseLabel` makes nothing except its returned object, which could also come from a pre-made table.
